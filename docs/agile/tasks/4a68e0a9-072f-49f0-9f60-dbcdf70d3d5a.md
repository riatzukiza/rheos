# Admit direct blocker reporting through the Promethean FSM

## Context

[Rheos issue 4](https://github.com/open-hax/rheos/issues/4) records canonical
`move` and `status-update` refusals for `todo -> blocked`, and a `move` refusal
for `incoming -> blocked`. Reporting an observed obstruction must not require
pretending that a task has reached a later lifecycle stage.

The inspected personal-fork base is
`11811264a308d406cb612aefa1dad40818675e5e`; upstream main is
`ef3c4abf1ea75199486f693e9470df3fec88dd49`. The relevant FSM, domain decision,
transition writer and CLI source are identical at both revisions. Only
`breakdown` currently enters `blocked`. The source declares a blocked WIP limit
of 15, but the existing edge uses `:always-allow`; `evaluate-transition` only
enforces a limit for `:wip-available`.

This is an upstream implementation plan. The existing Foresight consumption
story retains integration ownership and must consume a qualified immutable
Rheos revision after this plan is reviewed and implemented.

## Outcome

Allow a task in an explicitly reviewed, unfinished Promethean source state to
report an actual blocker through the existing FSM and transition writer, without
inventing progress or weakening ordinary forward gates. Record the true source
state in the canonical status-change event and preserve every historical ledger
byte.

## Scope

- Propose direct entries to `blocked` from `incoming`, `accepted`, `breakdown`,
  `ready`, `todo`, `in_progress`, `testing`, `review` and `document`. The existing
  `breakdown` edge remains valid; the review must settle this exact source set
  before implementation. `icebox` is intentionally outside the proposed active
  work set.
- Keep `done`, `rejected`, `archived`, unknown statuses and arbitrary custom-FSM
  sources excluded from these new entries. Preserve the existing same-status
  `blocked -> blocked` no-op contract.
- Use `rheos.backend.law.fsm` for the decision and
  `rheos.backend.infra.transition/move-task!` for writes. CLI `move`, CLI
  `status-update`, HTTP and MCP retain this shared authority.
- Preserve the existing non-blocker transitions, named forward checks, command
  gates and blocked exits. In particular, `in_progress -> review` continues to
  require its build gate, and the existing `blocked -> breakdown|ready` edges
  retain their current behavior. A blocker event supplies no build, readiness,
  review or completion approval.
- Keep the existing `kanban.status-change` event vocabulary and emission path;
  record the actual `from`, `to`, task/project identity, source and write ID.

## WIP decision for planning review

The proposed policy is that an observed blocker can be reported even when the
blocked column contains 15 or more tasks, matching the existing
`breakdown -> blocked` admission behavior. Its count remains visible operational
information, not a reason to suppress truthful reporting. This proposal does
not silently remove the declared limit or alter execution/review WIP checks.

Planning review must explicitly settle whether to adopt this policy or require
capacity enforcement. If enforcement is chosen, specify the operator-visible
refusal and a canonical way to retain the blocker observation, without recording
a successful transition or walking false intermediate stages. Do not create a
second ledger or alternate write path. An unresolved WIP decision prevents
implementation readiness.

## Non-goals

No replacement engine, parser, sidecar, root FSM override, new lifecycle command,
global CLI installation, live board migration or shared-runtime mutation. No
default-FSM/custom-FSM expansion, automatic resume, new blocked exit, or bypass
of build/review/completion gates. No Foresight-local implementation of this law.
No retroactive rewrite/reordering of events or receipts, and no claim that the
issue's historical refusals were freshly reproduced by this documentation PR.

## Acceptance criteria

- [ ] Native planning review settles the exact source set, WIP policy, three-point
  estimate, risks and verification scope; every finding has its canonical
  disposition. Rheos admits a lawful ready transition before implementation.
- [ ] In the red phase, canonical FSM tests reproduce missing direct entries
  from the accepted sources at the pinned base. Terminal/unknown/icebox cases
  stay refused. Existing non-blocker decisions and check identities remain
  equal to their baseline, including the build-gated review edge and both
  blocked exits.
- [ ] Implement only the accepted canonical law and required adapter behavior.
  Fixtures cover blocked counts below, at and above 15 under the settled WIP
  policy; execution/review WIP enforcement remains unchanged.
- [ ] Real compiled CLI fixtures exercise both `move` and `status-update` in
  independent temporary task roots with explicit private EDN configuration.
  They update the actual source card to `blocked`, append exactly one canonical
  status-change event per successful move, and preserve identity and source
  metadata. No fixture targets a live board or shared watcher/service.
- [ ] Seed the fixture ledger with valid existing events and retain its original
  bytes/hash. Successful writes preserve that exact prefix; refused writes
  preserve the entire card and ledger; repeated blocked no-ops add no duplicate
  status-change event. Canonical Rheos/event-ledger code supplies parsing and
  event authority.
- [ ] Terminal/unknown source attempts return the documented nonzero refusal
  through both CLI surfaces and leave files unchanged. Forward command-gate
  failures still refuse and write nothing. No newly successful path is
  presented as qualification to resume, become ready or complete work.
- [ ] Hosted tests/build/lint bind the eventual implementation head and dependency
  revisions; standalone source dependencies and CI qualification consume their
  existing owner lanes rather than duplicating bootstrap work here.

## Risks

Expanding entry edges can be mistaken for permission to bypass an ordinary
forward check; complete non-blocker decision comparisons and explicit event
meaning guard against that interpretation. WIP refusal can erase practical
visibility of a real obstruction unless the accepted policy retains it through
canonical operations. Shared watchers, task roots and ledger writers can
contaminate fixtures; use private paths and preserve original prefixes.
